# rtun-manager: профили VPS и деплой

> **Статус.** `rtun-manager deploy` подключает SSH-транспорт (`RusshRemote`, крейт
> `russh`) и запускает пайплайн на VPS. Проверено только компиляцией и юнит-тестами
> на моке. Реальный сервер не проверялся, поэтому инструкция по ручной установке
> в [server-setup.md](server-setup.md) остается основным путем. Контракт модуля
> описан в [deploy-design.md](deploy-design.md).

## Что делает инструмент

`rtun-manager` — CLI для работы с сервером RTUN:

- хранит профили VPS: адрес, порт, пользователь, путь к SSH-ключу, домен и email (`vps add`, `vps list`, `vps remove`);
- ставит сервер на VPS по SSH-ключу, создает пира и пишет клиентский `.conf` (`deploy`);
- конвертирует клиентский конфиг между `client.toml` (формат демона) и WireGuard-подобным `.conf` (`conf to-wg`, `conf from-wg`).

Команды `vps` и `conf` не ходят в сеть.

Сборка из корня репозитория:

```bash
cargo build --release -p rtun-manager
```

## Требования к VPS

Требования проверяет шаг `Probe` будущего деплоя; сейчас они описаны здесь
для ручной установки.

- Ubuntu 22.04 или новее, либо Debian 12 или новее.
- Архитектура x86_64.
- Вход под root. Установщик `install.sh` запускается от root.
- Домен, указывающий на VPS: A-запись на публичный IPv4 и, если есть IPv6, AAAA-запись.
  Домен нужен для TLS-сертификата Let's Encrypt и для транспорта `ws-tls`.
- Открыты порты `443/tcp`, `443/udp`, `80/tcp` (ACME) и SSH.

## Профили VPS

```bash
rtun-manager vps add <имя> --host <IP или домен> [--user root] [--port 22] [--key PATH] [--domain DOMAIN] [--email EMAIL]
```

Пример:

```bash
rtun-manager vps add main --host 203.0.113.10 --key C:\Users\me\.ssh\id_ed25519
```

- `<имя>` — до 32 символов: латинские буквы, цифры, `-` и `_`. Имя должно быть уникальным.
- `--host` — домен или IP. Допустимы буквы, цифры, `.`, `-` и `:`.
- `--user` по умолчанию `root`, `--port` по умолчанию `22`.
- `--key` — путь к приватному SSH-ключу. Пароля у команды нет: ни флага, ни запроса.
- `--domain` и `--email` сохраняются в профиле, но `deploy` берет их из своих аргументов (см. ниже).

Остальные команды профилей:

```bash
rtun-manager vps list           # строки вида: имя<TAB>user@host:port
rtun-manager vps remove <имя>   # удаляет только профиль, на VPS ничего не меняет
```

## Деплой

```bash
rtun-manager deploy <имя> --domain vpn.example.com --email admin@example.com [--peer laptop] [--index 2] [--repo-root .]
```

| Аргумент | Обязательный | По умолчанию | Правило |
|---|---|---|---|
| `<имя>` | да | — | профиль, добавленный через `vps add` |
| `--domain` | да | — | должен содержать точку |
| `--email` | да | — | должен содержать `@`; нужен для Let's Encrypt |
| `--peer` | нет | `laptop` | буквы, цифры, `_`, `-`, до 32 символов |
| `--index` | нет | `2` | от 2 до 254; задает адрес клиента `10.66.0.<index>` и `fd66:1::<index>` |
| `--repo-root` | нет | `.` | корень репозитория с `target/release` и `packaging/` |

Что делает команда сейчас: находит профиль, проверяет домен, email, имя пира и
индекс, после чего возвращает ошибку. Подключения к VPS нет.

Ход деплоя по проектному дизайну (шаги `Step` в `rt-deploy`):

1. `Probe`: `uname -m`, `id -u`, `/etc/os-release`.
2. `Upload`: копирование `rtund`, `rt-ctl` и `packaging/server/*`.
3. `Install`: `install.sh --domain ... --email ...`, идемпотентно.
4. `Peer`: `rt-ctl add-peer`. Существующий пир считается ошибкой, потому что приватный ключ пира печатается один раз.
5. `Fetch`: получение серверного конфига и сборка клиентского `.conf`.
6. `Verify`: `systemctl is-active rtund nginx unbound`.

При ошибке деплой останавливается и показывает шаг и stderr.

Пока эти шаги не выполняются, поэтому ручная установка по
[server-setup.md](server-setup.md) остается рабочим путем.

## Конвертация конфигов

```bash
rtun-manager conf to-wg client.toml -o rtun-laptop.conf
rtun-manager conf from-wg rtun-laptop.conf -o client.toml
```

- `to-wg` читает `client.toml` и пишет `.conf` с секциями `[Interface]`, `[Peer]` и `[Rtun]`.
- `from-wg` читает `.conf` и пишет `client.toml`.
- Флаг `-o` (или `--output`) обязателен.
- Неизвестные ключи в `.conf` вызывают ошибку. Комментарии `#` разрешены.
- Секция `[Rtun]` — расширение RTUN, обычный WireGuard-клиент ее игнорирует.
- Файл записывается через `write_secure`, как и профили.

Команды `peer add`, `status`, `conf export` и `conf import` описаны в
design-документе, но в текущем CLI их нет.

## Где лежат профили

Путь к `profiles.toml` определяется так:

1. Если задана переменная `RTUN_MANAGER_HOME`, файл лежит в `$RTUN_MANAGER_HOME/profiles.toml`.
2. На Windows: `%APPDATA%\rtun\profiles.toml`.
3. Иначе: `$XDG_CONFIG_HOME/rtun/profiles.toml`, а если переменная не задана, `~/.config/rtun/profiles.toml`.

Если файла нет, список профилей пуст.

## Что хранится и что не хранится

В `profiles.toml` хранятся: имя, host, port, user, путь к ключу (`key_path`), домен и email.

Не хранится:

- пароли: у команд нет параметра пароля, и в структуре профиля такого поля нет;
- содержимое приватных SSH-ключей: сохраняется только путь;
- WireGuard-ключи: профили их не содержат.

Тест `save_and_load_round_trip_without_secrets` проверяет, что файл профилей не содержит слова `password`.

Файлы `.conf` и `client.toml` содержат приватный ключ клиента (`PrivateKey` или `private_key`).
Их нужно считать секретами и не передавать в открытом виде.

## Статус по коду

Проверено тестами (`cargo test -p rt-proto -p rt-deploy -p rtun-manager`, все проходят):

- `rt-proto`: разбор и запись `.conf`, round-trip без потерь, отказ на неизвестные ключи и дубликаты секций (43 теста в крейте).
- `rt-deploy`: пайплайн на `MockRemote`. Проверяются порядок шагов, отказ на не-Ubuntu/Debian и не-x86_64, отказ без root, остановка на ошибке установки, отказ при существующем пире, невалидный ввод не доходит до shell (8 тестов).
- `rtun-manager`: профили, дубликаты, удаление, allowlist имен и хостов, файл без секретов (4 теста).

Не проверено и не реализовано:

- SSH-транспорт не проверен на реальном сервере. Тесты используют `MockRemote`; интеграционный тест `RusshRemote` помечен `#[ignore]` и требует переменные `RTUN_TEST_SSH_*`.
- Host key принимается без проверки `known_hosts` (TOFU). Повторные подключения не защищены от подмены.
- Ключи с парольной фразой не поддерживаются.
- Пароля нет: `deploy` работает только с SSH-ключом из профиля.
- Аргументы `--domain` и `--email` из профиля не используются, их нужно передавать явно.
- Команды `peer add` и `status` отсутствуют.
- CLI-команды `conf to-wg` и `conf from-wg` не имеют интеграционных тестов. Проверена только библиотечная часть `wgconf`.
- Ни один шаг деплоя не запускался на реальном VPS.
